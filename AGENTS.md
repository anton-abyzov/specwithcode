# SpecWithCode

SpecWithCode is an independent, open-source (MIT) workbench for native coding agents. SpecWeave owns portable intent, task claims and handoffs; the app owns environment-local sessions and control. Required third-party notices remain in THIRD_PARTY_NOTICES.md.

## Product identity and licensing

- Present SpecWithCode as an independent product. Lead with its own settings, provider orchestration, portable specs, handoffs and machine workflows.
- Preserve required copyright and permission notices in THIRD_PARTY_NOTICES.md and distributed artifacts; product positioning never authorizes removing required attribution.
- SpecWithCode is open source under the MIT License (LICENSE, Copyright (c) 2026 Anton Abyzov). Third-party code keeps its own license; never relicense it, and keep THIRD_PARTY_NOTICES.md and the notices in Settings complete.
- This is a public repository. Never commit secrets, personal paths, machine names, customer data or private reports; keep them under ~/.specwithcode or another folder outside the repository.

## Naming

In anything a person reads (UI copy, docs, reports, commit and PR text), call the product SpecWithCode on first mention and "the app" after that, never "Studio" or "SpecWeave Studio". Branch, repo, path, package and tool names stay literal (`feat/studio-plan-progress`, `specweave-studio`, `studio_thread_list`). The identities that must not be renamed are listed in `docs/studio/naming.md`.

## Isolation and ownership

- Production runs use Node 22.20. Build tools may require a separately scoped Node 24 runtime; report that distinction. Never change shared toolchains or provider installs to fix a build.
- CLI: specweave-studio. Default loopback port: 8319. Private home: ~/.specwithcode for new installs; true legacy standalone ~/.specweave-studio/userdata or dev keeps precedence, otherwise an existing branded root survives managed identity installation; legacy-only roots and explicit STUDIO_HOME remain supported. Runtime options use `STUDIO_*` only; other products' environment variables are ignored and must never select their installs or stores.
- Check active owners, branch, increment and ledger before claiming work. Preserve native sessions, services, schedules and dirty worktrees. Idle-looking metadata does not authorize takeover.
- Never point test servers at live stores, symlink credential folders, copy OAuth tokens or start provider turns while importing history. Use a new private test home and scratch repository; omit credentials, pending work and auth sessions from any explicitly authorized snapshot. A check that must drive the live app creates its project with `origin: "automated"` and deletes it when done.
- Stop only the exact PID you spawned or an exact newly owned launchd service after verifying its identity. Never pattern-stop providers, apps or dev servers.
- Never open a running service's database (`userdata/statev2.sqlite`, `-wal`, `-shm`) with sqlite3, Python or Node, not even read-only, and never copy or delete those files while it runs: that can crash the service or lose its newest writes. Use `specweave-studio db query` or `db snapshot`, `scripts/studio-fleet/live_database.py` or `scripts/lib/live-database.mjs`. Server code never opens those files through node:fs. See docs/operations/live-database.md.
- Hosted relay/cloud and telemetry are disabled by default. Self-update is on by default but reads only the app's own release feed; Settings > About and `SPECWITHCODE_DISABLE_AUTO_UPDATE=true` (legacy `STUDIO_DISABLE_AUTO_UPDATE`) turn it off. Direct private pairing remains. Never introduce other products' endpoints or infer subscription entitlement.

## Focused checks

- Read the canonical SpecWeave increment, claim only the assigned task under your own identity and edit its files. Work in the existing checkout your thread was given, on your own branch: no `git worktree add` unless the project's Use worktrees switch is on, and no extra clones unless it is on or the user asks (owner's rule, 2026-11-02). While it is off, the `git` SpecWithCode puts on the PATH of a thread in the project's own checkout refuses `git worktree add`; do not work around it. If the user asks for a separate worktree, tell them to turn on Use worktrees in the project's settings first: while it is off, a thread launch asking for one gets the project's checkout. When the switch is on, put the worktree under SpecWithCode's configured worktree root (never a sibling of the checkout in ~/Projects/github) and create it without the vendored `.repos` tree: `git worktree add --no-checkout -b <branch> <path> origin/main`, then in it `git sparse-checkout set --no-cone '/*' '!/.repos/'` and `git checkout <branch>`. Run a normal `pnpm install` there, and never symlink another checkout's node_modules, because workspace packages would resolve to that checkout's source. Remove it (`git worktree remove`) once its PR merges or closes. Before removing any worktree, check no SpecWithCode thread still uses it. A copy of the repository you made in the scratch folder is yours to clean up the same way: remove it, or at least its `node_modules`, once its PR merges or closes, and keep only the evidence. The hourly cleanup removes the installs of a copy that sat unused for a day (docs/operations/merged-clones.md), but each one holds several gigabytes until then.
- Run the smallest focused behavior/contract test and relevant production web/server build. No repo-wide tests, lint or typecheck unless requested.
- Foundation audit: node scripts/studio-brand-audit.mjs. Preserve the exact third-party MIT license, legal notices, reference trees and cryptographic/replay/binary fixture bytes.
- Physical-phone availability, restored native continuity and authenticated subscription capacity require actual outcome evidence; viewport fixtures, a fresh session and prepared slots do not prove them.

## Architecture

Typed WebSocket requests become commands. The pure orchestrator serializes commands and chooses events. The event sink atomically commits events, projections, command receipts and outbox effects. The effect worker performs I/O such as provider turns and checkpoints, feeding results back as commands. Git checkpoints support diff/restore.

- apps/server: auth/API/WebSocket, native adapters, orchestration and checkpoints. Read docs/internals/effect-services.md before adding Effect services.
- apps/web: React/Vite; desktop wraps web via Electron/IPC; mobile is separate React Native.
- packages/contracts: typed wire schemas and small derived helpers.
- packages/client-runtime: shared client commands, permissions, state and connections.
- packages/shared: focused utilities with subpath exports.
- .repos: read-only reference trees. Never edit, import, package or bulk-transform them.

Keep side effects at adapter/service boundaries, orchestration pure and transports thin. Mutations use createEnvironmentRpcCommand; protected methods belong in CLIENT_GUARDED_RPC_SCOPES. Destination environments authoritatively check grants at execution. Test UI permission availability and server rejection.

Drain OrchestrationEffectWorkerV2 or await a specific persisted event/Deferred in tests; do not hide races with sleeps. Preserve same-origin routing for local, SSH and private HTTPS clients. Do not bake localhost VITE_HTTP_URL/VITE_WS_URL into remote bundles.

Check chat, Settings, command palette, keybindings and reverse actions. Preserve native plans, approvals, queues, steering and checkpoints. Keep unknown quota/offline/errors explicit. Avoid continuously repainting animations and gratuitous state payloads. Use existing semantic UI variants; layout belongs to the parent. Typefaces, sizes, corners and colors come from the design tokens in docs/studio/design-guidelines.md: interface text is sans (serif is for report documents only), sizes and corners are scale tokens, status colors are semantic tokens. `apps/web/src/designTokens.guard.test.ts` enforces it.

Document changes to user tasks and durable architectural constraints, not copies of types. No publication, remote push or release service is implied by local implementation. Require manual acceptance only when the user or increment acceptance criteria explicitly request it. Record unverified installed/native behavior as a proof limit, not an automatic closure blocker for every UI/auth change.
