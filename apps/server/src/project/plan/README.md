# Planning core integration

Planning is optional. `read` returns an empty native plan without persisting a row. Chat, worker dispatch and project memory do not depend on this service or a CLI.

The integration lane registers `061_ProjectPlan.ts` after migration 060, exports `projectPlan.ts`, provides `ProjectPlanService.layer`, and adds thin RPC/UI adapters. The layer requires SQL, ProjectStoreV2, ProjectionStoreV2, ProcessRunner, FileSystem and Path. It shares ProjectAdmission with lifecycle operations. Migration triggers purge all plan text, assignments and captured process output on logical or physical project deletion.

All mutation actors must come from authenticated transport context, never a caller-provided agent argument. Human RPC adapters set `{kind:"user"}`; MCP adapters derive the actual bound thread ID. `configure` and `verify` are human-only. Do not expose a tool that lets an assistant call verification with a forged user actor. Show the exact saved executable, arguments, directory and timeout before the explicit user verification action. This core runs that command without an implicit shell and bounds duration/output; it is not a sandbox.

Native mutations use expectedRevision CAS. Changing acceptance/task definitions increments contentRevision and invalidates current verification while keeping historical receipts. Agents cannot release, change, delete or silently take over foreign claims. A human can explicitly release a task by supplying the exact expectedOwner and revision, including when its worker has been deleted. `reported_done` is an assertion; only an actual successful ProcessRunner receipt can produce `verified`. Verification records a command ID before execution. Retries (including after service reconstruction) return that receipt without executing again; an interrupted process retains an honest `unknown` result. A deliberate new test uses a new command ID. Late results after changed acceptance/assignment are `stale`; late results after project deletion cannot recreate data.

SpecWeave mode stores only a configured root and increment ID. Every read loads the exact bounded spec.md and ledger.jsonl under that approved project root. No scan, install, pickup, claim, handoff or alternate ledger runs. Malformed/missing sources fail visibly, and switching authority is explicit. The read-only fold supports the 3.0.6 ledger events and lease semantics; old owners remain visible. External `done` remains `external_unverified`, because a ledger assertion is not independent test proof. Unknown future event formats require adapter work instead of silent fallback. `renderPlanMarkdown` produces a portable export of a native plan, never an authoritative second ledger.

For this release, the configured root must resolve within `workspaceRoot`, and source file symlinks must stay within that configured root. Use the umbrella folder as the Studio project when its authoritative ledger lives above a child repository. An unrelated or parent-folder binding is rejected, even on the explicit human configuration action.

Tests use in-memory SQLite and temporary directories, real Node child processes for success/failure/timeout/output bounds, and a controlled runner for concurrent/restarted/stale-result cases. They do not exercise a real model or production store.
