# Project workspace headless fixture

This harness renders the production project workspace/settings/memory/usage/routines components, plus compiled production CSS. Host queries, provider operations, model pickers, asset loading/previews, Markdown parsing, and the native ChatView are explicit in-memory fixtures. It verifies frontend routing payloads and UI behavior; it does **not** prove real coordinator dispatch, provider resume, persistence, or backend isolation.

Build `apps/web` first. From `apps/web`, run with Node 22.20:

```sh
PWDEBUG=0 PLAYWRIGHT_HTML_OPEN=never node tests/project-workspace/serve.mjs
```

In another terminal, run `check.mjs`. Install/use a Playwright runtime compatible with an available browser, or specify `PLAYWRIGHT_MODULE` (absolute path to its `index.mjs`) and `PLAYWRIGHT_EXECUTABLE_PATH`. It always launches headless and never opens the HTML reporter. The port is 5788 unless `PROJECT_UI_PORT` names another; the fixture fails if the port is occupied, and `timeline-detail-check.mjs` follows the same variable. Stop only the PID you started.

```sh
PWDEBUG=0 PLAYWRIGHT_HTML_OPEN=never node tests/project-workspace/check.mjs
```

`PROJECT_UI_OUTPUT` selects the evidence folder (default `/tmp/studio-project-ui`). Checks cover desktop and 390px mobile, light/dark, a scoped worker link, exact `sourceThreadId`, memory draft preservation, incomplete usage, project-specific routines, exact deletion confirmation, and viewport bounds. Generated screenshots and JSON remain outside the repository. Native server/provider integration is a separate required release check.

`environment-check.mjs` additionally checks Personal project settings, simultaneous folders/repositories, revision-bound save and preparation payloads, explicit MCP configuration/check/tool grants/revocation, and desktop/tablet/phone layouts. Set `UI_EVIDENCE_DIR` to a new directory and optionally `PLAYWRIGHT_MODULE` / `PLAYWRIGHT_EXECUTABLE`. Host operations and tool discovery in this harness are synthetic; they are not native Git, MCP, sign-in or provider proof.

`machine-check.mjs` opens the fixture with the project on two machines (`?machines`). It checks that this computer runs the coordinator when nothing is saved, that the machine name under the composer opens the coordinator machine choice, and that a chosen machine survives a reload. A one-machine project shows the name with nothing to choose.

`starter-check.mjs` opens the same fixture as a project with no threads (`?fresh`, and `?fresh=empty` for an empty folder). It checks the greeting and its three chips at the top of the coordinator, the first tasks in the Threads pane, that choosing one sends its request to the coordinator once, keyboard use, dark theme and the phone layout. `?fresh&failed` adds a coordinator turn the host could not start: the project pane must say so with the host's reason, offer "Open the coordinator thread" (the coordinator's own full page, never the right pane), and keep the first tasks on offer. The suggestions come from the real builder with synthetic repository signals; the host's own reading of a folder is covered by `apps/server/src/project/ProjectStarterSuggestions.test.ts`.

`thread-cards-check.mjs` checks how the coordinator's answer names threads: every thread the sentence names is a blue chip with a status dot, and the thread it started that turn also gets a bordered card under the message with its quick actions ("View thread" always; "Create PR" or "View PR" when the thread's checkout and pull request call for it). It checks light and dark, and that "View thread" and a chip each open their thread in the right pane.

`mention-check.mjs` opens the coordinator with a reply that names a worker by its plain title (`?mention`): "Sent to the Release Chrome extension worker." must render "Release Chrome extension" as that worker's chip, which opens it in the right pane, while the same title inside inline code stays text. Screenshots in light and dark go to `PROJECT_UI_OUTPUT`; `PROJECT_UI_PORT` follows the fixture's port.

`knowledge-check.mjs` opens Project settings > Memory with the Project knowledge card. Without `?knowledge` the host's config never arrives, so the card shows no meter, no buttons and no request to update. `?knowledge=old` is a host whose config lacks the capability: the card asks to update SpecWithCode on Development Mac and shows no meter, buttons or search. `?knowledge` is a built index that threads still receive in full: it checks the mode line, how full the index is, each source, the left-out files, a search with its passages, dates and the short line a screen reader hears, that Search and Rebuild index send the project's id, and that Rebuild index shows "Indexing…" at once and stays off. `?knowledge=search` is a project past what threads receive in full: the bar warns at 82%, the card says when full sends return, and a search with no match says so. At 1440 px and 390 px, light and dark, nothing in the card spills past its edges. Status, search and rebuild are synthetic (`knowledge-fixture.ts`); the index itself is covered by `apps/server/src/project/knowledge/*.test.ts`. Screenshots go to `PROJECT_UI_OUTPUT`; `PROJECT_UI_PORT` follows the fixture's port, as it does for `check.mjs`.

`legacy-check.mjs` opens a project from before projects had settings (`?legacy`): no saved coordinator model, no coordinator thread, no project default. Once the host's providers arrive the composer must name the host default (Claude Opus 5.5 here) and never ask for a model; while they load (`?legacy=loading`), and while they are in but Claude still awaits its first check (`?legacy=checking`), it must say "Loading models" and the starter note must say models are still loading. The server side, saving at startup the model an existing project already names (its coordinator thread's or its defaults'), is covered by `apps/server/src/project/ProjectSettingsNormalizer.test.ts`.

`pane-check.mjs` checks the thread's right panel (the "Open a surface" launcher and its tabs) under `?routed`, where the open thread lives in the URL as `?thread=<id>` like the real route. Arriving at a thread never shows that panel: a URL load, a Threads list row, a coordinator chip, a "View thread" card, reload, Back and Forward, and reopening after closing the thread pane all land with it closed, including panels an earlier version saved open (they are migrated once, and current-version data is closed on every load). The toggle brings a thread's remembered tab back, and a browser whose session ends closes its now-empty panel. The native ChatView is a stand-in here; the panel state is the real `rightPanelStore` and `useHideRightPanelOnLeave`.

`enter-send-check.mjs` types into the coordinator composer the way a person does. Enter sends the message and Shift+Enter breaks the line. An Enter dispatched during an input method's composition (after `compositionstart`, with `isComposing` or `keyCode` 229) does not send, and the Enter after it does. Cmd/Ctrl+Enter also sends. A 600 px desktop window still sends on Enter and keeps focus in the composer, while a 390 px touch phone keeps Return as a new line and sends from the Send button, and so does an 844 px landscape touch phone. Set `UI_EVIDENCE_DIR` to a new directory and `PROJECT_UI_PORT` when the fixture runs on another port.

`followup-check.mjs` opens the fixture with follow-ups typed in workers before they went straight to the worker (`?followups`). The coordinator conversation must leave out a follow-up it only passed back to its own worker, and its reply, and keep one it moved to another worker with its "Moved to" line. A reply typed in a worker on this machine must not reach the coordinator. It checks light and dark at 1440 px.

`timeline-detail-check.mjs` opens the coordinator with runs and work items attached to its turns (`?activity`). It checks each level at 1440 px and 390 px, in light and dark.

In every level the commentary that starts "Consolidate the skills" and carries `triage-notes.md` shows that thread's card and the file once; Concise moves both to the turn's answer.

- **Normal** shows the conversation as before, with no activity blocks.
- **Verbose** puts an open `<details>` under the finished turn's answer. The summary reads "Started 2 workers, checked threads, ran 1 command and read 1 file". Below it are its six steps, worded in the past tense and showing what each worked on. A second block for the running turn sits above the progress line, and that turn's current step is worded in the present tense. Each block collapses and reopens.
- **Concise** hides the commentary before the answer and keeps the person's messages and each turn's last reply.

The project header's trigger carries `sws-icon-button-on` while the level is anything but Normal. Set `UI_EVIDENCE_DIR` to a new directory.

`report-check.mjs` opens the coordinator with a worker that reported back a long review of increment 0973 and a coordinator relay of it (`?report`). At 1440 px and 390 px, light and dark, it checks that the worker's report is a card (title, word count, the `0973-budget-vs-actuals` increment chip, opening lines, never the whole report), that "Open report" shows the whole report in a reader that fits the viewport and names the folder saving uses, that "Save to increment" saves once and turns both surfaces to "Saved", and that the coordinator's relay folds behind "Show full message" and, opened, draws its rule, keeps "Show less" on screen from the middle of the block, and folds back with its top in view. It also checks the thread beside the report: live, with its pending approval and a composer that sends while the report stays open, and a strip of the thread's artifacts above it (newest first; a tile puts that artifact on the left and is marked current); Escape from the composer still closes. Opened from the coordinator's artifacts, the viewer borrows the coordinator's own composer (one `#project-prompt`, inside the overlay) and hands it back to the page with its draft. The native ChatView there is a stand-in. Saving is synthetic here; writing the file beside the increment is covered by `apps/server/src/project/ThreadReports.test.ts`. Set `UI_EVIDENCE_DIR` to a new directory.

`answer-check.mjs` opens the same coordinator with the worker answering a plain question in about 340 words instead (`?report&answer`): a few paragraphs and a short list, no headed sections. At 1440 px and 390 px, light and dark, the answer must sit whole in the chat with no report card, no "Open report" and no "Show full message". `ANSWER_MEASURE_ONLY=1` records what a build shows instead of asserting, for a before capture. Set `UI_EVIDENCE_DIR` to a new directory.

`recovery-check.mjs` verifies coordinator failure recovery at 1440px and 390px. Saved screenshot/file attachments are re-staged using production recovery logic and sent with fresh pending references. A missing saved asset or failed upload aborts the entire retry and preserves the independent composer draft. A saved Copilot selection remains selected while Studio explains its additional-folder limitation; an explicit Codex choice enables retry. Asset queries, byte responses, uploads and provider operations are synthetic. No real provider turn, live project setting or permission changes are made. Set `UI_EVIDENCE_DIR` and `PROJECT_UI_PORT` for output and port selection.

The rollout fixture also checks the current installed coordinator layout and native error details. `?recovery=full-access` keeps a saved Copilot coordinator on its actual existing full-access/default policy even though the host's startup default is restricted; the retry preserves both files. Restricted-policy Copilot remains blocked and can be changed explicitly to Codex. No fixture changes project or provider permissions.

`resolution-resize-check.mjs` uses `?resolution&routed` to exercise failed/limited worker Resolve and Reopen against a reactive in-memory shell, all four status headings, waiting counts, divider drag and reload persistence, worker/expanded layout, narrow-window clamping and mobile bounds. Run with `PROJECT_UI_PORT=5799` (or a chosen free port), `PROJECT_UI_OUTPUT`, `PLAYWRIGHT_MODULE` and `PLAYWRIGHT_EXECUTABLE_PATH`. No provider or live persistence is exercised.

`resolved-details-check.mjs` uses `?resolution&history&routed` to verify legacy archived history is grouped under Resolved, the selected shell reaches embedded history consumers outside the active index, a visible Reopen action clears archive and settlement, and history remains available. This fixture uses in-memory shells and sample history, not a live backend or provider. The actual `useThreadShell` context fallback is separately covered by `entities.selectedThreadShell.test.tsx`.

`follow-latest-check.mjs` opens the long conversation with two projects (`?stream&switch`) at 1440 px and 390 px. At the end, a streamed reply, a picture loading late in the reply and in the person's own message, a row above growing, a scroll the browser makes on its own, a click on a message, the end of a turn and a narrowed and widened panel must all leave the reader at the end with no "Jump to latest". After a wheel up, the message at the top must stay at the same offset while a reply streams, a picture loads and the panel resizes, with "Jump to latest" marked New. Wheeling back to the end, End and the button each resume following with no further click, and coming back from Beacon lands on the latest. `follow-latest.json` records every step. `FOLLOW_MEASURE_ONLY=1` records failures instead of stopping. Set `UI_EVIDENCE_DIR` to a new directory.

`scroll-follow-check.mjs` opens a long coordinator conversation (`?stream`) at 1440 px and 390 px, wheels up, then streams a reply in six growing steps, adds a worker's routed message and types three lines in the composer. The reader must stay at the same `scrollTop` (and the page must not scroll) with "Jump to latest" marked New; the button returns to the end, where a reply is then followed, and the person's own message returns to the end from further up. `scroll-offsets.json` records every step. `SCROLL_MEASURE_ONLY=1` records failures instead of stopping, to measure a build without the fix. Set `UI_EVIDENCE_DIR` to a new directory.

`project-return-check.mjs` opens two projects behind the real `ProjectWorkspace` (`?stream&switch`), where a project left for another stays mounted under a hidden Activity, at 1440 px and 390 px. A first visit opens at the latest message; leaving Atlas for Beacon and coming back lands on the latest again while following it, shows a reply that arrived while away, and returns a reader further up to the same message (with "Jump to latest" offered, marked New once something arrived), including after rapid switching and after older messages mounted from the top. No older messages mount on the way back. "Jump to latest" sits above the composer, has an accessible name, works from the keyboard, reaches the newest message and follows again. `project-return.json` records every step; `PROJECT_RETURN_MEASURE_ONLY=1` records failures instead of stopping, to measure a build without the fix. Set `UI_EVIDENCE_DIR` to a new directory.

`routines-layout-check.mjs` opens the Routines tab of a busy code project (`?routines=coordinator`: an active watch, three paused routines, a failed run, a long name and one run by hand), an empty one (`?routines=none`) and the personal assistant's.
