# Updates

SpecWithCode keeps two things current on a Mac: the desktop app and the SpecWithCode service that the fleet installer runs under launchd. The desktop app reads releases from the public `anton-abyzov/specwithcode` repository; the service agent reads the repository named in its config (the same public repository by default). Settings > About controls both.

## Startup recovery and verification cost

A service that is still starting can time out before it answers the desktop's saved-session probe. The client retries recognized transport failures and HTTP 502/503/504 within a 60-second retry window. It reports a missing HTTP response honestly instead of inventing HTTP 500. Real 401/403 responses and real HTTP 500 remain terminal; retrying never recreates credentials or changes permissions. An already-running request retains its transport timeout, and no new request starts at the retry deadline.

Database verification remains fail-closed. A small local cache can reuse a table's typed and legacy proof only after validating the exact schema and the table, index and overflow page contents in the current read snapshot. Missing, damaged or incompatible cache data, unsupported SQLite capabilities and uncertain WAL state fall back to the existing scan. The cache stores hashes and counts, not conversations or credentials. A cold cache can cost more than an uncached read; subsequent reads avoid repeated JSON serialization of unchanged tables. On the cached full-scan path, event logs needed by the restart's append proof are still scanned while their reference lines are kept. Eligible held updates use the stopped-clone page proof described below; neither path promises constant-time verification. Migration, authentication, idle-work and rollback checks remain required.

## Settings

| Setting                         | Default | What it does                                                                                                                                                                                                               |
| ------------------------------- | ------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Check for updates automatically | On      | The app checks every hour; the service agent checks every hour as well. Off stops all background checks.                                                                                                                   |
| Download in the background      | On      | A found release downloads and is verified right away.                                                                                                                                                                      |
| Install automatically           | On      | The app installs the next time you quit it. The service installs once no session has worked for 10 minutes; a thread that is only waiting on a usage limit does not count as working. Off means you install from Settings. |
| Update track                    | Stable  | Stable takes plain versions such as `0.2.1`, even when GitHub marks the release as a prerelease. Nightly takes `-nightly` builds.                                                                                          |

The SpecWithCode service row shows the installed version, what the agent is doing and a **Check now** or **Install now** button. Install now and the sidebar's **Update now** do the same thing: they do not wait for quiet.

## Update now

Update now installs a downloaded service release while work is still running. If anything is running it first asks, listing the tasks that will be interrupted, queued messages that will be cancelled, questions that will be closed and terminals that will close. Then:

1. the service holds itself for the update: new messages, scheduled tasks, pull request polling, channel messages and new terminals wait or are refused with "SpecWithCode is installing an update. Send this again after it restarts.";
2. it cancels queued messages, interrupts running turns (each ends `interrupted`, so you can continue it after the update), releases every agent process, closes questions, cancels background effects that do not settle within 20 seconds and closes terminals, keeping their history;
3. the desktop writes the install request with `installMode: "force"` and `installHoldUntil` (15 minutes ahead), and the agent retries the snapshot every 10 seconds within one pass until the service is quiet, instead of waiting for a quiet period. If new work slips in before the restart and `update.py` refuses the apply, the agent snapshots and applies again, up to twice. If the snapshot still refuses for leftover processes, running tasks or active sessions after 2 minutes (a provider that never answered its interrupt, or a command left running under a closed terminal), the agent runs `update.py --reap --request <installRequestedAt>`; open questions and finishing steps alone never trigger it, and neither does a request cancelled meanwhile. The helper verifies the service as for a snapshot and refuses unless that very process is held for that request: while held, the service keeps `updates/hold.json` (its pid, when the hold began and when it ends; removed when the hold ends), and `config.json` must still force-install the same request, made during the hold and not cancelled. It checks this again before every signal. It then stops every process beneath the service except its supervisor (the caffeinate with the LaunchAgent's arguments; any other caffeinate is work), its own server browser and its own SpecWithCode Connect tunnel (the cloudflared it installed under its `tools` folder and started itself), by PID and only while each still has the pid, owner, start time and kernel-resolved executable recorded for it (SIGTERM, then SIGKILL after 10 seconds, all within 60 seconds). Nothing outside the service's process tree is signalled, and the service keeps running, so its hold stays in place. This happens at most twice a pass, 2 minutes apart (a newer request taken on gets two of its own), and never past the retry window the agent is snapshotting in; the record, kept as `updates/receipts/reap-*.json`, lists what was signalled even when the reap stops part way. Leftover processes alone are reaped early: after 20 seconds of such refusals, and again 20 seconds later, before any full reap, the agent runs `update.py --reap --stale --request <installRequestedAt>`. That reap makes the same checks and also refuses unless the database shows no running task, queued message, pending request, unfinished step or active session, first and before every signal. It stops only processes that started before the hold began (`hold.json`'s start; a ps start time counts as the end of its second, and in a repeated daylight-saving hour as its later reading) with nothing started since beneath them, such as a command left under a terminal the hold closed. Anything newer, such as a git the held service started, its parents, and any process whose start time cannot be placed wait for the full reap. Early reaps do not count toward its two. A refusal for leftover processes no longer names the service's own server browser, which the update stops itself, unless nothing else is there. The service's own SpecWithCode Connect tunnel never keeps an update waiting: the restart replaces it, so no snapshot, apply or reap counts or stops it, and a refusal does not name it unless nothing else is there. Any other cloudflared, including one started in a terminal, counts like any other process.

If `update.py` refuses the apply before the restart because a process appeared under the service after the snapshot ("Owned service has unexpected descendants", in its preflight or in the process check right before the restart, which puts every pointer back first), the agent snapshots and applies again like any other refusal before the restart. While `updates/hold.json` shows the hold has not ended, the next snapshot can reap that process; without a hold it waits for the process to exit. If no quiet snapshot comes before the retry's window ends, the request ends as the refused apply did: "did not install … See the update receipt", naming that apply's receipt.

A full snapshot checks the processes beneath the service before its database read as well as after it, so a stray process refuses it in seconds rather than after a read of several minutes; the capture after the read is the one the proof keeps. An automatic pass that finds a newer install request, a cancellation, automatic installs turned off or another repository in `updates/config.json` before its snapshot ends without taking it ("Automatic installation stopped because update settings changed."), as it would after the snapshot, and the request is served by the next pass at once. The agent runs under launchd's `LowPriorityIO`; it starts the apply helper and a held (`--request`) snapshot at the default disk I/O policy, while its other snapshots stay throttled. The receipt records the helper's policy as `diskIoPolicy` (`0` is the default, `3` throttled, `null` where it cannot be read).

`fleet_rollout.py` holds M4 through the service's own CLI, `service prepare-update --stop-work --hold --reason install --json`, which first shipped in 1.0.45. An older service serves the same hold to its own Update now, but its CLI has no such command, so the rollout refuses to ask it for an unheld forced install and says so; choose Update now in the app on that Mac instead (see Releasing).

`update.py`'s checks are unchanged: the forced path only drains the service until those checks pass. **Cancel update** releases the hold and writes `installCancelledAt`; the agent stops retrying and reports "Update cancelled". The hold also ends on its own when the agent reports an error or finishes, and after 15 minutes. An error ends only the hold for the request its pass served: each status a pass writes names that request in `state.json` (`answeredInstallRequestAt`, `""` for an automatic pass). A pass that refused an earlier request, or an automatic pass that refused, after Update now was pressed leaves the new hold to the pass that serves it, which the agent runs next. An error that names nothing (`null`) still ends the hold when it is newer than the request, as before: it comes from an older agent, from a pass that failed before it named a request (reading its settings or its installation, or an unexpected failure before then), or from a pass that reports an install an earlier pass left interrupted while a request was pending, which may be that request's own install. When the helper restarts the service while it was held for a request, because it lost its database locks or runs on a deleted database log, the restarted service holds itself again for that request. `updates/database-restart.json` names the request, when the old hold would have ended (`until`) and how far it could have moved (`ceiling`: 110 minutes, `HOLD_MAX_MS`, from when the old hold began, or from the request when that hold was itself carried, capped by the ceiling a carried hold names or by the end of one a service from 1.0.108 to 1.0.112 carried, which never moved, and never short of `until`). The new hold ends where the old one would have, or 20 seconds after the new service starts if that is later, and moves with the agent as the old one did, never past the ceiling. A service from 1.0.108 that predates `ceiling` reads only `until` and holds to it, as it did before; so does a newer service under a marker without `ceiling`. A request for a newer release from the fleet or the CLI, written while a pass works on an older one, ends that pass without refusing the request, and a run that pass owned ends `cancelled`: the next pass checks again, finds the newer release and installs it. Update now for a newer release, pressed while no run is live and no held request stands (during an automatic pass, or one serving an unheld request: a worker's version-bound one from the fleet, or one the CLI wrote without a drain), ends such a pass the same way, and the next pass claims the press's run. While the fleet's held request stands on M4, a press only follows that install, and the newer release takes another press once it has ended. While a run is live, every window only follows it: its pass installs the release the run names, and a newer release takes another press once the run has ended.

Self-update is on by default and reads only SpecWithCode's own releases; the app never accepts the original upstream feed. `SPECWITHCODE_DISABLE_AUTO_UPDATE=true` (or the older `STUDIO_DISABLE_AUTO_UPDATE=true`) forces it off for a machine. While it is off, the switches in Settings > About show off and cannot be turned on (they report what the service's `updates/config.json` holds), the SpecWithCode service row says automatic checks are off, and Check now and Install now still work.

## One update run

From 1.0.67 an Update now press is one durable run that the app, the service and the update agent share. Every window, a reload and a relaunched app follow the same run, and none of them shows Update now, Restart to update or Retry while it is not terminal.

**The run record, `updates/run.json`.** The desktop's main process creates it for a press (`begin`), with O_EXCL (a temporary file linked into place), so two windows pressing at once make one run and both follow it. It holds `runId`, `rev` (bumped on every write), `targetVersion`, `appTargetVersion`, `requestedAt`, `deadlineAt`, `phase`, `owner`, `heartbeatAt`, `leaseUntil`, `message`, `receipt` and `endedAt`. Phases go `preparing`, `requested`, then `downloading`, `waiting` and `installing`, and end `verified`, `failed`, `cancelled` or `expired`. An ended run is never written again; the next press archives it to `updates/runs/<runId>.json`, keeping the newest five.

**The lease.** The agent claims a requested run whose `runId` its config names (`installRunId`, beside `installRequestedAt`) and whose lease is free, at the start of a pass, or when a pass that owns no run takes on the run's request part way (one written while it served a request from the fleet or the CLI). While it works it renews `leaseUntil` (now plus 90 seconds) with a heartbeat every 5 seconds, mirrors its status into the run's phase, and writes the outcome, with `handledInstallRequestAt`, when its pass ends. Its log lines carry UTC timestamps. A pass that a request for a newer release ended (the fleet's or the CLI's; a press while a run is live follows that run and writes no request) ends its run `cancelled`, saying which release replaced it: `config.json` no longer names the run, so no later pass would take it on.

**One clock.** `deadlineAt` is the start plus three times the last verified install's time (`expectedMs` from `install-progress.json`), between 10 and 30 minutes, and 30 minutes when no time is known. It replaces the agent's forced-retry window and the request's 10-minute life for a run's request, also one a pass takes on part way, and it is the hold the desktop writes. A request for the same release that a pass takes on while it owns a run (the CLI's, or the fleet's written as the press was made) is served by its own life, as it would be without the run. A forced one also keeps its own window, which the service's hold follows (`installHoldUntil`). A plain one is retried for as long as the press's hold times it, 15 minutes from the press, so the hold ends with that pass instead of staying on after it. The run then ends with that pass, and the request keeps the outcome the pass gave it. The fleet does not ask again while a press's held request for the release it rolls out stands, which it does until the agent answers it without installing it. Windows never fail a run on a timer of their own: a heartbeat older than 2 minutes shows "No progress for 2 min, still installing" in amber, with no button. Main kicks the agent again when the lease has lapsed for over 10 seconds (at most every 30 seconds, before the deadline), and ends a run as `expired` only when nothing owns it, it is 5 minutes past its deadline, the install helper has written no progress for 2 minutes and no install marker exists. Main also ends a run nothing owns in four other cases, never one an agent holds: a `preparing` run whose window went away (older than 150 seconds, or made before this desktop process started) ends `expired`, and a new press takes over instead of following it; a run whose install request could not be written to `config.json`, or whose agent could not be started, ends `failed` at once with that reason; a run whose target the service already runs (state.json, or the helper's `verified` result) ends `verified`, also when the fleet or the CLI wrote the request that installed it. A cancel or an expiry withdraws the request in `config.json` only while that file still names the run's own request, so a newer request from the fleet or the CLI is never withdrawn on its behalf.

**What the windows show.** The toast and the sidebar read the run: the helper's step i of n with elapsed and expected time from `install-progress.json`, "Service is back, finishing checks" once the service restarted, and, while open questions keep the install waiting, the threads they are in (asked every 30 seconds without stopping work). While an automatic install waits for quiet, the sidebar shows a short hint under Update now ("Waiting on 2 open questions"), naming the threads in its tooltip. It reads the same live thread state as Needs you: a question answered, or a thread resolved or archived, drops out at once and the service is asked again. The hint can be dismissed for that version. Questions and approvals left 2 minutes on a quiet thread, and anything a resolved or archived thread waits on, no longer hold the automatic install (see the stale-wait sweep in `ServiceUpdatePreparation`); questions and approvals are asked again after the restart. Try again or Restart now appear only on a terminal run, and each outcome is reported once on the computer.

**The app half, `updates/run-app.json`.** Only the main process writes it. Once the service reports the run `verified`, main downloads the app release if needed and installs it, with or without a window open; the record says `relaunching` before the install starts. A relaunched app reads it before its first update check: on the target release the run is done, still on the old one it reports "App update did not apply". An accepted install whose quit has not begun within 5 seconds is taken back at once: the app gets its backends back and the app half ends failed with "SpecWithCode did not restart to install the update." An app whose quit began and that is still running 75 seconds after the install reports "App update did not apply". Restart now installs again on the same run.

A window that names no app release (`appTargetVersion` null, as when Update now is pressed before the window heard of the app's update) gets the one the desktop knows: what this launch's update check found, else a download an earlier launch left in electron-updater's cache, and asked before the first check, that check runs at once instead of after the 15-second startup delay. The desktop's answer is kept only when it is the run's `targetVersion`. A newer app release would wait for a service release the agent does not install, and an older cached one may be gone from the feed, so either would end the app half failed; the run is then service-only and the app updates on its own. The macOS bundle-swap updater keeps the staged copy a run names at startup instead of clearing it.

**The app never runs ahead of the service.** A downloaded app release is staged for install-on-quit, or installed by a restart, only once the local service runs that release or a newer one (`appActivationGate.ts`); a restart before then is refused with `service-behind`. A service that needs a manual step (`manual-required`) will not catch up on its own, so the app stops waiting for it. Machines without a managed service, dev and nightly builds have nothing to wait for.

**Compatibility.** The agent advertises runs with `runSupport: 1` in `updates/state.json`. The desktop writes run-era requests only when it sees it, and `installRunId` is its own config key, because older agents reject unknown keys inside `installRequest`.

| Desktop                 | Agent                    | What happens                                                                                         |
| ----------------------- | ------------------------ | ---------------------------------------------------------------------------------------------------- |
| With runs               | With runs (`runSupport`) | One run: lease, one deadline, the app installed by main after `verified`.                            |
| With runs               | Older (no `runSupport`)  | `begin` answers unsupported and the window updates as before runs: its own hold, request and timers. |
| Older                   | With runs                | No run is created; the agent handles the request as before (`installRunId` absent).                  |
| With runs, run going on | Agent later downgraded   | The run is followed to its end; main expires it when nothing owns it past its deadline.              |

## Private releases

SpecWithCode stores no GitHub token. Each check uses `STUDIO_UPDATE_TOKEN`, `GH_TOKEN` or `GITHUB_TOKEN` when set, otherwise it asks the `gh` login on the Mac (`gh auth token`). The token stays in memory and goes only to `api.github.com`; asset downloads that redirect to GitHub's storage host get no token. If checks say the releases are private, run `gh auth login` once on that Mac.

## The desktop app

Signed builds (`studioBuild.signed` in the app's `package.json`) use electron-updater and Squirrel.Mac. Unsigned builds, which is every build today, use the bundle swap in `apps/desktop/src/updates/macSwapInstall.ts`: the app downloads the release zip named in `latest-mac.yml`, checks its sha512, unpacks it next to itself, checks the bundle id and version, and swaps the bundles after it quits. A failed swap puts the old app back. The app must run from a folder it can write to, such as Applications, not from the disk image.

Releases before 1.0.0 installed as `SpecWeave Studio (Alpha).app`. The update to 1.0.0 still lands at that path, because an update always installs where the running app is. On its first launch 1.0.0 renames its bundle to `SpecWithCode.app`, updates Launch Services and opens itself again (`apps/desktop/src/updates/macBundleName.ts`); later swaps from an old-named bundle also install under the new name. It skips the rename when the folder is not writable, when `SpecWithCode.app` already exists, or after one failed try for that version. If both apps end up side by side, SpecWithCode.app moves the older same-id copy to the Trash. The download is staged in `userData/pending-update/staged.noindex`, so Spotlight does not list it as another app.

After an unsigned swap macOS may ask again for permissions such as Accessibility or Screen Recording, because an ad-hoc signature changes with every build. Signing removes that.

## The SpecWithCode service

The managed service updater defaults to the public `anton-abyzov/specwithcode` release feed. Public releases can be checked and downloaded without signing in to GitHub. An explicit `repository` in `updates/config.json` is preserved, including a private feed that requires its own GitHub access. Updating the helper does not rewrite existing settings or enable opted-out updates. Macs without a config file use the public default on their next pass after the new helper is installed through the supported bootstrap command below.

The service cannot replace itself, so the desktop installs a small agent beside it: `scripts/studio-fleet/update_agent.py` and the modules it imports, `update_agent_reap.py`, `update_agent_cache.py`, `update_agent_recovery.py` and `update_request.py`, copied together to `~/.specwithcode/install/updater/` (`~/.local/share/specweave-studio/updater/` before the home migration) and run by the launchd job `com.specweave.studio.<identity>.updater` every 10 minutes. It reads `<studioHome>/updates/config.json` (written by the desktop) and writes `state.json` (read by Settings). On each pass it:

1. searches the newest 30 releases on the chosen track for the highest newer release whose verified `studio-update.json` supports the installed source;
2. refuses the release unless the plan lists the installed source commit, so only reviewed upgrade paths run on their own;
3. downloads the runtime and helper archives and checks them against `SHA256SUMS` and the helper manifest;
4. waits until two snapshots 10 minutes apart show no running session and no change; an open SpecWithCode terminal also counts as busy (an install request retries the snapshot every 10 seconds instead, for 2 minutes, or until `installHoldUntil` for Update now);
5. runs that release's own `update.py` with the plan's arguments.

An install request, from Update now or from a plain Update, whose apply `update.py` refused before the restart because work or a process beneath the service changed after the snapshot, with every pointer as it was, snapshots and applies again in the same pass, up to twice. Only then does the request end as "did not install". Each retry waits for quiet in a window of its own, counted from the refusal (2 minutes for Update; for Update now, until the hold ends, at most 15 minutes), so a long staging or backup before the refusal does not use it up. A retry that never applies ends the request as the refused apply, with its receipt; it never lapses later as "expired before it could start". When the retry's own snapshot refused with a cause the person can act on (the service lost its database locks and needs a restart, or no longer matches its installation), the request ends with that message instead. A cancel written while the last retry snapshot ran ends it as "Update cancelled". A newer request taken on during the pass, such as Update now chosen while a plain Update retries, gets attempts, retries and a retry window of its own, and a refused apply belongs to the request it ran for, so a newer request never ends as an older one's refusal and is never left pending unanswered.

An automatic install refused before any restart or installation change can receive at most two retries, after 10 and then 20 minutes, within a 24-hour window. Each retry requires an intact refusal receipt, unchanged installation and fresh quiet checks. An install request that ended as an apply refused before the restart changed nothing either (`lastInstall.refusedBeforeRestart`), so it does not hold automatic installs; they go on, each with its own quiet checks. Other failed installs, such as one that failed after the restart, remain held for Install now. A verified intermediate upgrade is followed by a new discovery pass; the agent never installs several releases in one loop.

An install request names the version the app showed: the desktop writes `installRequest: {at, version}` beside `installRequestedAt` (same `at`). The agent installs only that version; when it would install another (a newer release found meanwhile), it settles the request with an error asking to choose Update now again. A request the agent has not started within 10 minutes of `at` lapses with an error asking to choose Update now again, and never installs at a later quiet moment. A request written while a pass holds the agent's lock gets one more pass as soon as that pass ends, instead of waiting for the next 10-minute run. A newer request picked up while a pass retries is checked the same way before it is installed. A request without that record, from an older desktop, keeps the earlier behaviour.

The old service keeps running while `update.py` stages the release, and a thread waiting on a usage limit writes on its own about every five minutes: an event, its command receipt, that thread's projection row and the projection cursor. Each guarded check reads, in the same transaction, which rows were appended after the snapshot it compares with, and accepts them when every earlier event and receipt row is byte-identical at its position, projection rows changed only for threads or projects that have new events, and every other protected table, the set of projects and threads, auth rows, settings file and environment id is unchanged. A new release that saves a project's settings when it starts (for example the coordinator model an older project already names) writes the same shape: a project event, its receipt and that project's projection row, so it carries forward too. Edits or deletes of earlier rows still abort, before the restart or by rolling back after it. The appended rows stay in the database the new release opens; the receipt's `appendedLogRows` counts them.

After staging, `update.py` checks the prestate once: after it publishes the new release under `~/.specwithcode/install/releases/`, where it stays inert because no pointer names it, and before it writes any pointer or `owned-updates` folder. A refusal there leaves only that unpointed release: a retry of the same archive reuses it, a later verified update prunes it like any other release no pointer names, and `fleet_health` counts it until then. A release already published under that name that differs from the archive is refused before that check.

Once the new pointers are written, `update.py` writes its install gate, `<identity home>/updates/install-gate.json`, and keeps it until the new release is verified or rolled back. While the gate is live the service, old or new, starts nothing on its own: no scheduled routine, webhook run, "Run now", limit recovery, sweep or new message, and a run interrupted by the restart is marked failed only after the gate opens. Releases up to 1.0.46 read a new gate only on their 5 s poll; later ones see it on the next check. So `update.py` waits `INSTALL_GATE_SETTLE_SECONDS` (12 s) before comparing the protected rows, or `HELD_GATE_SETTLE_SECONDS` (2 s) when the running service holds itself for this very Update now request (`updates/hold.json` names its pid and `updates/config.json` still asks to force-install the request made during the hold, as `update.py --reap` checks): a held service has refused every command that starts work and skipped its background ticks since the hold began, so the gate's poll cannot let a run start. Failure receipts name which settle ran as `gateSettle` (`held` or `full`); a verified receipt shows it as `timings.gateSettle`. It then compares them again right before the stop, then stops the service and clones the database (see the migrations section below). A routine that ran in between (on M4, 1.0.43 to 1.0.45, a 5-minute routine ran during the online backup those releases took while the service ran, and the update rolled back) now stops the update before the restart, with the old release still running and its pointers restored; an install request snapshots and applies again, while an automatic install refused there stays held for Install now. With `--allow-existing-browser-heartbeat`, both comparisons also prove any auth change the way the check after the restart will (an existing, active session of a supported kind, within the session counts and the restart window), so a reconnect that check would roll back, such as a CLI session or a revoked one, stops the update here as "Native work changed before restart: auth (…)", handled the same way. Without that flag, auth must stay exactly as it was, so any reconnect stops the update before the restart. Schedule rows stay byte-identical across the restart: no write to them is needed while the gate is live.

Prestate auth comparisons retain SQLite cell types and the complete auth schema while allowing what a connect writes on its own: the connection timestamp and the app version the client reports (`client_app_version`, `AuthSessions.ts` `setClientConnectionRow`, shown in the sessions list only). A desktop app relaunched into a new release reports its version on its first connect; before 1.0.61 that landed between the agent's snapshot and the apply and refused every first attempt with "Guarded prestate changed: rows". The surface written beside it (`client_surface`) stays guarded, because the heartbeat proof after the restart classifies sessions by it: a changed surface refuses the apply before the restart ("Native work changed before restart"), which an install request retries. Snapshots using an older invariant format (`studio-auth-invariant-v2` before 1.0.61) fail closed and must be refreshed before an update; read an older receipt back with its own release's helper.

Each pass also removes downloads and helpers for the installed version or older, including ones a failed or manual install left behind. After a verified update, `update.py` deletes old unpacked releases under `~/.local/share/specweave-studio/releases/`. It keeps the new release, the previous one (the rollback target), any release that another identity's `launch.sh` or `installation.json` names, and anything unpacked in the last hour. The removed names are listed in the receipt's `prunedReleases`. It then removes, under `prunedLeftovers`, what nothing else did: staging folders a killed helper left in `install/incoming`, release bundles and `.tar.gz` files there older than the installed release, and, past the newest 10 of each kind, update receipts (an `update-`/`prestate-` pair with its log, and `reap-`, `idle-agents-` and `database-restart-` records) with the `owned-updates` folder a finished one names. A held or failed rollback, an apply that died with pointers moved, an unreadable receipt, one that `state.json`, `run.json` or the install marker names, this update's own and anything written in the last hour stay, and so does anything in `install/incoming` with another name.

Older pre-update state copies in `~/.specweave-studio/backups/` go once a verified update's helper has exited, so the service is not held while they are deleted: `update.py` starts `update.py --prune-state-backups <receipt>` in its own session (`stateBackupPrune` in the receipt says whether it started), which waits for the installation lock, keeps this update's copy, all copies referenced by unresolved recovery in any local identity, and unclassified copies; older explicitly completed copies may go immediately, and adds what it removed to the receipt's `prunedStateBackups` with `stateBackupPruneAfterInstall`. It acts only on a verified receipt in the identity's own `updates/receipts` folder. The child runs at background disk priority, and an apply that finds the lock busy meanwhile is refused and retried. Before the copy, older copies beyond the two a verified update leaves go (copies failed attempts left; a helper writing its receipt elsewhere keeps only the newest older one, as before), and a disk too full for the copy prunes the older copies first, then the newest older one only when they cannot cover what is short.

Every copy of the agent ships the release it belongs to, in `agent-release.json` beside it (`{schemaVersion, version}`, written by `bundle.mjs` into the runtime's `studio-updater/` and by the desktop build into the app's `Resources/studio-updater/`, since 1.0.67). `update_agent.py --install-launch-agent` records the release it installed, with each file's sha256, in `updater/agent-release.json`, and never installs a copy over an agent of a newer release. A copy that belongs to no release, from a checkout, installs and removes the record, so any release replaces it. After a verified update, `update.py` installs the new release's agent the same way (`update_request.refresh_agent`; the receipt's `updateAgent` says what happened), and `update_request.py request` and `check`, which the fleet rollout runs, first install the agent of the release the Mac runs. They leave an agent of the same or a newer release alone, never set one up for an identity without its own launchd job (the agent's files are shared by every identity of the OS user, the job is not), and never run the installer of a release that records no agent (1.0.66 and older), since it would put its agent over a newer one. Outside a pass the installer works as the desktop's does (`installed`, `unchanged` or `disabled`), as when `remote_update.py` runs `update.py`. During one, as when the agent runs `update.py`, it writes the new files without touching launchd (`busy`): the pass goes on with the old agent, and the next run uses the new one. That pass would take on a request written meanwhile, and launchd starts no new run while it runs, so `request` and `check` give it up to 60 seconds to end before they write and kickstart (`AGENT_PASS_WAIT`; the rollout allows those calls 150 seconds), and report `busy` only when it still runs. A forced request never waits: it follows a drain whose hold lets go when no request arrives within a minute. A record is written only when every installed file is the installing copy's, so two installers running at once never leave a mix that a record vouches for. Before 1.0.67 only the desktop app installed the agent, so a Mac whose desktop app was old or never opened kept its first agent: M1 still ran the copy its 1.0.48 desktop installed on 10-16, which did not retry a refusal before the restart, and its 1.0.66 install failed until that agent was replaced. A desktop app older than 1.0.67 still installs its own copy when it starts; the next update or fleet request replaces it.

Every `update.py` snapshot also carries `databaseCapture`: the complete schema (every `sqlite_master` object, column and foreign key) and a typed-cell hash of every table, read in the same read-only transaction as the protected rows. It contains hashes, schema text and the `sqlite_sequence` counters, never other cell values. The prestate check compares it, the updater re-reads it just before the restart, and an update without `--allow-project-migrations` must leave the whole database unchanged after the restart (receipt `completeDatabaseContinuity: "verified"`). The capture accepts exactly what the guarded rows accept: rows a waiting thread or a project settings save appended (new event and receipt rows after earlier rows whose values and SQLite types are unchanged, the projection rows of that thread or project, the projection cursor and the forward-moving AUTOINCREMENT counters of those logs), and, in the checks before the restart, an `auth_sessions` heartbeat or reported app version whose invariant hash is unchanged (right before the restart, only one the heartbeat proof accepts, when the update allows heartbeats). After the restart an auth change is accepted only with a proven heartbeat. Every other table and the schema must stay identical. This covers tables the protected-row hash skips, such as `checkpoint_diff_blobs`, webhook delivery tables and `effect_sql_migrations`, and TEXT/BLOB or integer/real swaps. A migrating update records the capture but keeps the migration rules below (`completeDatabaseContinuity: "not-compared-migration"`). `database_continuity.verify_update_database` recomputes a saved byte-identical or heartbeat receipt against the live database; `network-transition.py` runs it for M4 locally and for M1 and M3 on their own host over pinned SSH, and records the results in `verifiedDatabasePreservation`. A prestate must come from the same updater version that applies it.

Each snapshot and check first asks, in its read-only transaction, whether the service is idle, and only then reads the rows: reading every table takes minutes on a large database, and a busy service is refused anyway. The proof, auth, appended rows and capture it records are the same as when the protected rows were read first, from the same snapshot; only which refusal comes first can differ when a database has several. The earlier rows of each log are hashed in the capture's own scan of that log, as `WHERE rowid <= <boundary>` reads them: the leading rows of the table up to the first later rowid, even on a page whose rows are out of order. A log with an index holding every column is read with that query instead, because a full scan can read the index where the query reads the table. An unexpected table name, then a busy service or an idle check that cannot run (a missing idle table, an undecodable or corrupt idle row), are refused before any row is read, where reading the protected rows first could meet a row it cannot read (a corrupt page or undecodable text) and refuse for that (`test-update-read-speed.py`, `RefusalOrder`). When a fault ends the read transaction (an I/O error, a full disk, out of memory) in a table the capture reads before a protected table's own fault, that fault is the refusal, because no snapshot is left to read again with the protected rows first. A database with a virtual table, such as an FTS5 index, is read protected rows first, then the idle check, then the rest, the order every database was read in before the single scan, so its records and refusals are exactly as before (`test-update-read-virtual.py`): a virtual table's module makes its rows on every read, two reads can differ, and a module may read its own tables to connect. Every table whose stored `CREATE` text does not start `CREATE TABLE` counts as virtual, so finding them connects no module. `statev2.sqlite` has none (SpecWithCode keeps its only FTS5 table in each project's knowledge index, a database of its own), and an SQLite older than 3.37 reads every database protected rows first, then the idle check, then the rest.

`update.py --allow-project-migrations` accepts a release whose migrations add tables and rebuild projections in one pass. Every project, thread and protected table must survive, and existing event history, provider, schedule, pairing and auth rows must stay byte-identical. New events and command receipts are allowed only with the same measured prefix proof described above. Auth schemas and every typed auth cell are checked independently of projection rebuilding; equal row counts do not prove preservation. Those protected tables are also compared by SQLite type through the snapshots' `databaseCapture` (receipt `migrationProtectedCells: "typed-verified"`), because the protected-row hash writes a BLOB as its hex text: a pairing credential, provider or schedule cell, or an earlier event rewritten as that text fails the update. Their table definitions, column lists and foreign keys must also stay identical: both hashes ignore column names, and a cascading foreign key would let a write to another table rewrite or delete protected rows later. So a migration that adds, renames or retypes a column of one of these tables fails even when the table is empty; new indexes stay allowed. A database without an `auth_sessions` table has no session to protect, so a migration may create that table, but only empty; a migration that drops it fails. The same holds for `auth_pairing_links`, `provider_session_runtime`, `scheduled_tasks` and `scheduled_task_run_receipts`: a migration may create them only empty. A migration may not add a trigger that names any of these tables, whichever table the trigger sits on, because it could write sessions or credentials after the update verified; other triggers, such as ones on projection tables that clean a project table, stay allowed. These checks cover the persisted schema only: a TEMP trigger or any other code the new release runs is trusted release code, like every runtime write. Once the old service has stopped (`launchctl bootout` and its exit, so launchd's KeepAlive cannot start it again mid-copy), it copies `statev2.sqlite` to `~/.specweave-studio/backups/pre-<commit>-<time>/`: an APFS clone of the database, `-wal` and `-shm` (well under a second), with the cloned log then folded into the cloned database, so the folder holds the same single `statev2.sqlite` and `settings.json` as before. A volume that cannot clone (`EXDEV`, `ENOTSUP`) gets SQLite's own copy instead. Before stopping the service it refuses when the backups volume has less than max(1 GiB, 10 % of the database plus the whole `-wal`) free (folding the log writes every page in it into the clone), or when too little of the apply budget is left for the old service's exit, the copy and the readiness wait; either refusal leaves the old service running. A stop, copy or start that fails starts the old release again on the untouched database. The receipt records `stopAttempted` before the stop and `serviceStopped` once the job is confirmed unloaded, so a `launchctl bootout` that left the old service running reads as a refusal, not a restart. The unused copy is deleted only once the old release is loaded again (`stateBackupDiscarded`); while the job stays unloaded or the launcher still names the new release, it is kept and named in `stateBackup` with `stateBackupKept`. If the new release fails its checks after starting, it stops the service, restores that copy and starts the old release, so the old binary never runs on a migrated database. If the restore fails, it keeps the new release with its migrated database instead.

An upgrade plan that permits existing browsers to reconnect during the restart must also pass `--allow-existing-browser-heartbeat`. This permits only bounded, existing-session changes proved by the heartbeat checker, on the service's web sessions (up to two browser cookies where the browser signs in by cookie, as on M4; the relay's one web token on a worker such as M1 or M3), up to four existing desktop app sessions and up to four existing phone or tablet app sessions (a bearer or DPoP token reporting the `desktop` or `mobile` surface, such as the iPhone app connecting directly or over the relay during the install). A CLI session, a cookie on any other surface, or a revoked or expired session is refused. The change it permits is a `last_connected_at` advance, a change in the app version a connection reported (`client_app_version`, a non-empty text of at most 64 characters), or both. The server writes the version on every connect but stamps `last_connected_at` only on a session's first open connection, so the version can change without a new heartbeat; version changes are recorded in the witness (`schemaVersion: 5`). It never permits credential replacement, a changed surface, new or deleted auth sessions, or an auth schema change. A migration with such a reconnect records `rowPreservation: "verified-migration"` and `authHeartbeatWitness`, retaining both actual table hashes. Without a migration, rows the services appended (a project settings save at startup, a usage-limit check) carry forward beside such a reconnect: the guarded rows and the complete database are checked as for appended rows, the heartbeat is proven against the old non-auth rows, and the receipt records `rowPreservation: "verified-appended-activity-and-heartbeat"` with `authHeartbeatWitness`. `network-transition.py` does not accept that receipt, as it does not accept `verified-appended-activity`. Without this explicit opt-in, any auth change fails the update. Auth schema transformations need their own explicit preservation proof.

For offline readback of a migration plus heartbeat receipt, use `verify_migration_heartbeat_witness` in `update.py` with the receipt's actual row snapshots and complete private current auth. When the receipt lists `migrationAddedColumns`, also pass its `before_capture` and `after_capture` (the two `databaseCapture` values). The migration witness includes before/after commitments to every auth cell and its SQLite type; the verifier checks those commitments, the heartbeat, and the migration constraints. A migration witness without typed commitments is rejected. If logs were appended, also pass `state=Path(<trusted-userdata-directory>)`: the verifier re-reads public rows, private auth and earlier log prefixes in one read-only transaction, requires that database to match the receipt's after-snapshot, and proves every earlier log row survived. Counts from `appendedLogRows` are not preservation evidence. Without that database read, replay rejects changed log hashes. A database that has changed since the receipt also fails closed. The older network-transition verifier intentionally accepts only byte-identical or heartbeat-only updates; a migration receipt does not authorize a network transition. These database receipts do not attest preservation of external native account directories.

Every receipt `update.py` writes from `prepared` on also carries `timings`, whole milliseconds per phase, each added when its phase ends: `beforeRead` (the first snapshot and its checks), `backupSpace`, `verifyAndStage` (archive check, staging and publishing the release), `prestateCheck` (the second snapshot), `swapPointers`, `gateSettle`, `checkBeforeRestart`, `stop` (the app's server browser), `finalCheck`, `serviceStop` (bootout and the old service's exit), `backupClone` (the stopped copy), `restart` (bootstrap of the new release), `readinessCheap` (until the new process answers with the new release), `readiness` (the one full read after the restart), `keptRelease` (letting go of the before read's lines a decided page proof used), `guardedComparison`, `cleanup` (pruning old releases and installing the new release's update agent), `watermarkSkip` (time booked to re-reads the read watermark let stand), `deltaRead` (time of re-reads `read_delta.py` answered without a full read) and `total` from the start of the apply. A failure adds `untilFailure` (the failed phase, up to the failure), and the receipt written when the rollback ends, or stops on a check, adds `rollback` and `total`. The receipt also names `stateBackupMethod` (`clone` or `sqlite-backup`). Nothing reads them back, and the proofs are unchanged. A `preflight` receipt keeps its five keys, because installed update agents accept no other key there.

The full database reads before the restart (the prestate check, after the install gate settles, and right before the restart) are skipped only when a read watermark (`read_watermark.py`) taken right before the last full read that passed is unchanged: `PRAGMA data_version` on one long-lived read-only connection, the inodes of the database, `-shm` and `-wal`, the database's size, the `-wal` header's checkpoint sequence and salts and its size, and the connection's generation. Any commit, replaced file, checkpoint, VACUUM, reconnect or failed read means a full read. `data_version` alone would miss a service that exited and removed `-wal` and `-shm`: its successor writes to new files the connection never sees, so the inodes are compared too, and a watermark whose database or `-shm` is no longer the file it opened reconnects. The connection keeps its SQLite locks while it is open; the lock checks in each snapshot probe through descriptors the watermark holds open, because closing a probe would drop them. After the restart a cheap poll waits, up to the readiness deadline, for a new process that answers with the new release; then at least one full read runs, even when the poll timed out, a read that fails is retried until the readiness deadline, and a mismatch still rolls back.

A held install reads the whole database in full once more before the restart when something other than auth commits after its before-read and nothing outside `auth_sessions` commits after the prestate read starts. Held, the prestate is measured against the helper's own before-read, so when the prestate re-read reads in full, the check after the gate reuses that read while the watermark taken right before it is unchanged. That read is checked against `before` like a fresh one, and the read that stands (`passed[0]`, which the proof after the restart confirms its mark against) and the `-wal` base `read_delta.py` compares with both move to it together. On M4 the 1.0.88 install read three times instead (`beforeRead` 261 s, `prestateCheck` 254 s, `checkBeforeRestart` 257 s) and rolled back with `TOO_SLOW_TO_RESTART`; the writer then, `StrandedSubagents.sweep`, no longer runs while the service is held. A commit outside `auth_sessions` after the prestate read still costs one more full read at the check that sees it. Before any such full re-read, the check after the gate and the one before the stop refuse with `TOO_SLOW_TO_RESTART` when less of the budget is left than the before-read took, so a read that could not finish in time refuses at once with the old service running. Each re-read `read_delta.py` could not answer is listed in the receipt's `readDeltaMisses` with the base it was measured against and its reason (`no-position`, `main-file-changed`, `wal-replaced`, `wal-reset`, `wal-shorter`, `pages-outside-auth` with the page count, `no-dbstat`, `virtual-tables`, `no-auth-table`, `activity-changed` or `read-failed`). Increment 1077 is planned to replace the remaining re-reads on a busy service.

A held, drained service still commits between those reads, so the watermark rarely lets one stand. Traced in `apps/server`: every connected browser, desktop and phone app stamps its auth session's `last_connected_at` (on M4 every few seconds, about 6 MB of `-wal` in 7 minutes), a reconnect also writes the surface and `client_app_version` it reports (#554), and a pairing or revocation writes a session; besides those, commands the hold does not stop (a project settings save, a usage-limit check, a user action in the app) append events, receipts and projections. The automatic starters are held. Before this change each such commit cost a full read of the whole database at every check, 40 to 68 s each on M4's 8 GB, where `orchestration_events` alone is 4.9 GB and the projections 1.5 GB. Three ways were weighed. Re-reading only the tables that may change does not help: the projections and logs a command may append to are most of the database, and the earlier rows of a log cannot be shown unchanged without reading them. Comparing an APFS clone taken at the first read with the stopped copy would move every refusal to after the restart, where today the old service keeps running and an older agent may retry; the checks before the restart and their messages are pinned by tests, so that was rejected. What remains is the commit the service makes every few seconds, the auth heartbeat, so `read_delta.py` proves from SQLite's own files that only `auth_sessions` changed and reads only that table. Before each read it notes the `-wal` file, its salts and the second-to-last valid commit frame (the last may not be published to readers yet), checking every frame's checksum as SQLite's recovery does. A later re-read opens a read-only transaction and lists the pages of every frame written after that frame in the same `-wal` generation. Any change to a table writes at least one page that still belongs to it (its leaf, an ancestor, or an overflow page of a row that stays), and the schema is page 1, so when `dbstat` places every one of those pages in `auth_sessions` or its indexes, every other table reads as before and only `auth_sessions` is hashed again: its protected-row hash, its typed capture hash and the auth invariant, exactly as the full read hashes them. The result is the earlier read with those entries replaced, compared by the same `same_guarded_rows`, capture and heartbeat checks with the same messages. Everything else reads in full: another page, a schema change, a checkpoint that reset the log, another `-wal` file, no `-wal`, a database file that is another file or was written since the earlier read (its device, inode, size, modification time or 100-byte header differ: a file renamed or copied over it, which the `-wal` cannot show, or a checkpoint into it), a virtual table, appended rows measured against other log positions, a failed read, or an SQLite without `dbstat` (python.org builds; macOS `/usr/bin/python3`, which runs `update.py`, has it). The one full read after the restart is unchanged. `test-update-read-delta.py` drives a real WAL database from a child process holding one connection, as the service does: 120 random commits (heartbeats, other auth edits, event edits, appends and deletes, overflow-page blob writes, projections) where every re-read that answers equals the full read of that moment exactly; protected changes beside heartbeats at staging, at the gate and before the browser stop still refuse before any restart; an apply whose only commits are heartbeats runs no full read before the restart (`[before, after-restart]`); and the re-read takes the same SQLite steps, about a millisecond, on a database twenty times larger, while the full read grows with it.

While it applies a release, `update.py` keeps `updates/install-progress.json` in the identity's home (`~/.specwithcode/<identity>`) current (0600, written whole and renamed, so a reader never sees part of one): `schemaVersion` 1, `version`, `receipt` (the receipt path), `phase`, `step` of `steps`, `phaseStartedAt` (moved at every lap, also one that keeps the step such as `watermarkSkip` or `deltaRead`, so `phaseStartedAt` minus the sum of `timings` is always the apply's start), `heartbeatAt` (at least every 5 s, also while one phase runs long), `expectedMs` (the `timings.total` of the newest earlier verified install's receipt; refusals and rollbacks are not counted), `timings` so far, `agentTimings` (the update agent's own whole milliseconds before this apply, which it passes in `STUDIO_UPDATE_AGENT_TIMINGS`: `requestWait` from the install request to its pass, then `beforeInstall` for the check and download, `verifyHelpers`, `snapshot` and `retryWait` over every attempt, and `total`; `{}` from an older agent. Receipts from `prepared` on carry it too, and the agent's `run.json` adds the `apply` it waited for the helper), `serviceRestartedAt`, and `result` once it ends: `verified`, `refused` (stopped before the old service stopped; any pointer it had moved is back, and the old service never restarted), `rolled-back` (the old release runs again after a restart: the new one failed its checks, or the stop, copy or start failed; the failure receipt then carries `serviceStopped: true`), `held` (the rollback stopped on a check) or `failed`. While a failed apply puts things back, `phase` reads `rollback`. A helper killed outright leaves `result` null and a heartbeat that stops moving. Only `update.py` writes it, and nothing in the update reads it back.

To install the agent by hand on a Mac without the desktop app (M1, M3), run the copy the installed release ships, so the record names its release:

```sh
release=$(/usr/bin/python3 -c 'import json, pathlib; print(json.loads((pathlib.Path.home() / ".specwithcode/m1/installation.json").read_text())["release"])')
/usr/bin/python3 "$release/studio-updater/update_agent.py" --identity m1 --install-launch-agent
/usr/bin/python3 "$release/studio-updater/update_agent.py" --identity m1 --status
```

The checkout's `scripts/studio-fleet/update_agent.py` installs the same way; it belongs to no release, so the next update or fleet request replaces it.

## Database size: compaction and `db reclaim`

The event log, `orchestration_events` in `statev2.sqlite`, keeps every snapshot the service writes. Most of them are superseded: a streaming message or tool node writes its whole row again on every change, and a thread writes a full thread snapshot on every visit, title or settings change. Projections are rebuilt from the log, so only the snapshots a rebuild reads matter.

### Scheduled compaction

`apps/server/src/persistence/StorageMaintenance.ts` deletes superseded events every 6 hours, first 10 minutes after the service starts (`ProjectionMaintenance.compactEventStoreWith`). What it deletes, and why a rebuild still produces the same projections:

- `node.updated` and `message.updated`: every snapshot of one node or message except the oldest and the newest. The projector writes the row from the payload alone, so the newest snapshot gives the same row. The oldest stays because a row's position is set by its first insert: SQLite assigns the rowid then, and a rebuild that started from a later snapshot would order rows differently.
- Thread snapshots (`thread.metadata-updated`, archive, settle, snooze, pin, reorder, runtime-mode and pull-request events): each payload is the complete thread and replaces the whole row, so one followed by a newer one is superseded. Every other event of the thread also bumps its `updatedAt`, which the newer snapshot carries too. `thread.visited` and `thread.marked-unread` are superseded only by a newer read-state or thread snapshot, because the in-memory reducer does not bump `updatedAt` for them. `thread.created` and `thread.deleted` are kept.
- Imported legacy (v1) events and their command receipts, which nothing reads once imported.

`turn-item.updated` and `subagent.updated` are never compacted. A rebuild assigns each turn item its timeline position on its first write (`orchestration_v2_turn_item_positions`), so those events stay intact. The test `ProjectionMaintenance.compaction.test.ts` writes interleaved history, compacts it, rebuilds every projection and compares every projection row, rowid included, with the projections the live projector wrote.

Each pass runs in pages of 100 events with a 2 ms pause between pages, each page its own short transaction, so the service stays responsive. After the first full pass, a pass reads only the threads with events newer than the last pass (`storage-maintenance.json` beside the database: `completedAt`, `fullPassAt`, `throughSequence`), and a full pass runs again at least every 7 days. A pass that stops early writes no state, so the next check runs it again.

Compaction never runs while an update may read the database. `update.py` writes `updates/database-snapshot.json` before every snapshot, refreshes it when an apply starts and removes it when the apply ends, whoever runs it: the update agent (also while its status still reads `downloaded`), an install request, or `remote_update.py`, which runs `--snapshot` and then the apply with no hold, request or agent status. A marker no apply removed lapses after 2 hours, and a snapshot that wrote a new marker waits 2 seconds before it reads, so a delete the service started just before is committed first. Before every delete the pass also asks `ServiceUpdateHold` whether the service is held for an update (including the install gate after a restart), whether an install request is open (a forced request needs no hold), or whether the update agent is waiting for quiet or installing. The answers are cached for a second, so right before each delete statement, holding the connection, the pass also reads the snapshot marker and `updates/install-gate.json` again with no cache and nothing in between; each delete is one page and commits well inside the 2-second settle. A snapshot that fails takes its marker back (it restores a live marker it refreshed, or removes the one it wrote), so the agent's retries never keep a marker alive. When any of them is true the pass stops before its next delete and the log reads `storage-maintenance.compaction.interrupted`. This matters because the updater compares the event log with its snapshot: an earlier row deleted after the snapshot reads as `old-log-row-changed` in the page proof and refuses the update. The marker covers updates run by a helper that writes it, so by this release and later ones; an older helper, as in a downgrade, can lose that race, and a refused attempt is retried. It never loses data.

Deleted rows become free pages inside the file; scheduled compaction does not make the file smaller.

### `db reclaim`

`specwithcode db reclaim --base-dir <home>` shrinks a stopped database:

1. It refuses while the service runs (`server-runtime.json` names a live pid that started before the file was written; a pid another process took over after a crash or reboot is ignored, and `--force-stale-pid` ignores one `ps` cannot date), while an update holds or drains the service, while an update helper's snapshot marker is live, while an install request is open or the update agent is installing, and while any other process has the file open (it takes SQLite's exclusive lock with no wait). From then on `statev2.sqlite.reclaim-lock` names it, and the service does not open the database while it does. Where `ps` cannot date that lock's pid (Windows, BusyBox, a timeout) the service treats it as stale and opens, and the exclusive locks still refuse the swap; another `db reclaim` treats it as live. Every refusal names the lock file: if no reclaim runs, delete it or pass `--force-stale-pid`. On Windows `db reclaim` refuses before it changes anything, because Windows cannot rename an open database; scheduled compaction still runs there.
2. It runs `quick_check` and the projection check, compacts as above in one pass, and checks the projections again.
3. Before it deletes anything it checks free space where the copy goes (the used pages plus 5 %, plus 256 MiB) and, when `--work-dir` is on another volume, beside the database too, then writes `VACUUM INTO <work-dir>/statev2.sqlite.reclaim-<time>`.
4. It checks the copy: `quick_check`, WAL mode, and a fingerprint compared with the source: every table's row count, a hash of every projection, receipt and v2 event row with its rowid, every `(event_id, sequence)` pair of the event log, the highest sequence and `sqlite_sequence`. `VACUUM INTO` keeps rowids, so every sequence stays where it was.
5. It closes the database, then takes exclusive locks on it and on the copy and keeps both through the swap, so a connection that opened meanwhile refuses it and one that tries during it waits or fails. Under those locks the source's `-wal` must be empty. A copy made across volumes is checked for size and synced to disk with its folder (`fsync`, `F_FULLFSYNC` on macOS). The copy, still under its lock, must end at the original's highest sequence with an empty log. Then, uninterruptibly (Ctrl+C and SIGTERM wait for it), it hard-links the original to `statev2.sqlite.before-reclaim-<time>` beside it and renames the copy over the database's path in one step, so that path always names a whole database. If the rename fails, nothing changed: it removes the extra link and any copy beside the database, and keeps the checked copy in the work folder. On a volume without hard links (exFAT) it renames the original away first and puts it back if the copy cannot move in. Should the database ever be missing with `before-reclaim` or `reclaim-<time>` files beside it, the service refuses to start, instead of creating an empty database or importing `state.sqlite` again, and names the file to move back. Nothing reopens the new file afterwards, so a service that starts as the locks close never turns a finished swap into an error. The service also refuses to go on when the file at the database's path changed while it opened it.

`--dry-run` changes nothing and can run beside a live service, because it reads through `?mode=ro&readonly_shm=1` like `db query`. It prints the file size, the free pages already in the file, the events and receipts compaction would delete by type, and the expected size after `VACUUM INTO` as a range (deleted text plus an estimate of 600 to 3,000 bytes of row and index overhead per event, since the rewrite also packs pages that were never freed). `--work-dir <dir>` writes the copy in another folder; on the same volume it is renamed into place, on another one it is copied beside the database before the swap, and a copy that breaks off is removed. Delete the `before-reclaim` backup once the service runs well on the new file; it holds the compacted original, not the history before compaction.

Measured on a copy of a 19.14 GiB `statev2.sqlite` (2,792,377 events): the dry run took 240 s and listed 946,462 superseded events (917,559 `node.updated`, 10,680 `thread.pull-request-synced`, 7,887 `thread.visited`, 7,877 `message.updated`, 1,724 `thread.metadata-updated`, the rest other thread snapshots), 1.56 GiB of text. `db reclaim` then took 639 s and left 15.15 GiB with 1,845,915 events, the last still at sequence 2,792,377. Rebuilding every projection from the compacted log and from the original log gave the same rows and rowids as each other and as the live projections; the rebuild took 488 s instead of 839 s.

### Why auto_vacuum stays off

`--incremental` sets `auto_vacuum=INCREMENTAL` on the copy, and `Sqlite.ts` can set it on new databases (`INCREMENTAL_AUTO_VACUUM_FOR_NEW_DATABASES`). With it, scheduled maintenance frees up to 16,384 pages per pass in `incremental_vacuum` steps of at most 64 pages behind the same update gate, and reports the pages the free list actually lost. `incremental_vacuum` declares no result column but frees one page per step, so the SQLite client steps every `PRAGMA` to completion (`nodeSqliteClient.ts`); a single `run()` step would free one page. Both are off by default because the page proof after the restart refuses any auto-vacuum database: `after_proof.py` raises `Refused('auto-vacuum')`, since pointer-map pages belong to no b-tree it can compare, and every update of such a database then takes the full second read (40 to 68 s on M4's 8 GB) instead of the page proof. Run `db reclaim` when the file has grown instead.

## Publishing a release

`bash scripts/release/release.sh <version>` builds, signs, publishes and rolls out a release; the
runbook is [releasing](./releasing.md). The plan it writes takes the installed source commits that
may upgrade on their own from the previous release's plan (`make_update_plan.py --previous-plan`),
plus any `--from-source <installed-commit>` given by hand. Take such a commit from
`update_agent.py --status` (`installedSourceCommit`) on the machine, not from `git rev-parse` of an
older tag: the history was rewritten on 2026-10-13, so releases up to 1.0.8 report source commits
that no longer exist in the repository.

A release without a plan shows "needs a manual upgrade" in Settings and is never installed on its own.

### Migration-capable plans and the post-restart page proof

A plan allowing project migrations still attempts the page proof. A schema change makes the proof refuse, so the full read with the migration baseline runs. With no schema change, the proof supplies the same rows and typed capture to the existing migration-preservation checks. Allowing a migration does not imply that one occurred.

### The old service's shutdown writes and the page proof

The page proof (`after_proof.py`) compares the database after the restart with the clone taken at the stop and with the read the checks before the restart passed. Commits the old service makes between the final check and its exit (the gap) used to leave the proof undecided: on M4, 1.0.76 and 1.0.85 held installs both fell back to the full read (178 s and 292 s). Two causes. The read before the restart pins a snapshot for minutes, so at the mark the `-wal` is past the 1,000-frame autocheckpoint; the old service's first commit afterwards copied every frame into the database file and its second restarted the log (`old-log-reset`). And SIGTERM cancels background work, which appends events and receipts (51 and 20 on 1.0.85) and updates projections, so the gap touches the logs (`gap-touches-log`).

Right before the final check, `after_proof.mark` starts a child process (`python3 after_proof.py hold <database>`) that opens a read-only transaction and keeps it until the clone is taken. While it reads, no checkpoint copies a frame past its snapshot, the log cannot restart, and the old service's last close cannot fold the log in and remove it. The one exception is a snapshot that read the database file alone (every frame already copied, read mark 0): the first commit may restart the log, and no later one can, because nothing is copied while the reader reads. After the final check, `after_proof.confirm` accepts the reader's snapshot as the reference only when the read watermark shows no commit since the read the checks passed. `after_proof.stopped` then builds the reference image beside the backups (`.page-proof-<pid>-<uuid>.sqlite`): an APFS clone of the clone with each gap page written back as the snapshot read it (its last frame up to the snapshot, else the database file's page) and the file cut to the snapshot's size. It lets the reader go and folds the log the old service could not fold into the live database (a TRUNCATE checkpoint, as that close would have done, with no service running), so the new release starts as it does after a clean stop. The fold must leave the live file with the clone's size and content on every page the old log wrote; a fold that trusted an index another process kept, and that never saw the log's last commit, refuses as `fold-differs`. The proof compares the live database with the reference image, so gap pages are changed pages like any other: kept tables and logs are compared row by row over their changed leaves, and a log may still only gain rows above where it ended. A page one table freed and another reused (an overflow chain a rewritten row gave up, taken by an appended event) puts both tables in the comparison. The image is removed when the proof ends or the update fails (its path is on the mark before the clone is made), and a helper that died leaves one that the next update removes.

Without the reader (it did not start, or lost its snapshot before the stop: `reader-lost`) or without the confirmation, the proof keeps the earlier rule: a gap page of a log, a kept table or a stream refuses and the full read decides. `afterProof` records `gapPages` and `referenceImage`. `test-after-proof.py` covers the 1.0.85 case on `node:sqlite` with the service's pragmas, a pinned log, shutdown appends and projection updates, the one restart after a read-mark-0 snapshot, an old event changed in the gap (refused by both reads), the confirmation through a real watermark, a fold that differs from the clone, and the refusals without the reference image.

### Kept lines: memory first, then disk

The proof hashes the largest tables again from the before read's sorted lines (`kept_lines.py`). Nothing used to be kept unless three times the database plus 4 GiB of memory was available: M4's 1.0.89 install (21.9 GB database, 128 GiB Mac) fell back to the full read with `reason: memory` and a 513 s readiness. A read-only pass on that database kept 26.7 GB of lines (20 GB of them `orchestration_events`) at a 39 GB peak.

The lines now stay in memory while the system keeps `headroom()` available, the larger of 8 GiB and an eighth of physical memory, with room left for the legacy lines a table builds after its typed ones; that is checked as each table is kept. When memory runs short, or there is no headroom at the start, the kept lists are written as the exact bytes they hash to a scratch folder in the service's `updates` folder, with only the byte offset of every line in memory, provided that volume has twice the database plus 4 GiB free on top of what the pre-update backup still needs. With neither, or when a write fails, nothing is kept and `afterProof` records `reason: memory`, `disk` (with `availableBytes`, `floorBytes`, `availableMemoryBytes` and `headroomBytes`) or `disk-full`. Twice the database (with its `-wal`) is an estimate, not a bound (BLOBs are hex, JSON escapes text), so every file also stops before the volume would drop below the margin plus the backup's reserve. Lines still held in memory move to disk, or go, before any later full read the update runs before the restart, unless memory for one more read their size leaves the headroom. The files are read with `pread`, so a disk error is a fallback, not a crash. A proof that ran records `keptIn: memory` or `disk`. The lines and the folder go when the proof finishes, and before the rollback's own full read when an update fails; a folder left by a helper that is no longer running is removed by the next one.

The helper compares pre-update auth sessions with its own first consistent read, rather than the agent's earlier snapshot. A sign-in or `service prepare-update` between those reads is part of the helper's baseline. Later auth changes must still pass the invariant check before the restart and the existing typed auth proof across it. Other rows and the complete database capture remain checked against the agent's snapshot.

Backup admission uses the clone-aware sizing and recovery-aware retention from PR #623, including its 2 GiB staging margin. A clone that later falls back to SQLite checks the full-copy requirement again before copying. Existing recovery guards remain in force.

For a forced Update now request, the agent passes `--request` when snapshotting. A helper that supports held snapshots validates the exact live hold and idle state, then captures metadata without hashing all rows. Apply validates the hold again and establishes its own full consistent database baseline, while still comparing identity, pointers, settings and processes against admission. Checks before and across the restart use that complete baseline. If no matching live hold exists, the helper uses the full snapshot, so forced CLI requests still work. A tagged admission whose hold expires or is cancelled before apply refuses. Older helpers ignore `--request` during snapshot and retain the full read. Automatic quiet-period updates retain full snapshots.

### Held updates and history verification

A forced request with a verified service hold uses a stopped-clone page proof when
its schema and SQLite layout support it. Admission and the checks before stopping
read idle state, authority tables, schema, and project/thread identities; they do
not serialize event or message history. The backup made after the exact service
stops is the history baseline. A pinned SQLite snapshot validates WAL checksums,
page ownership, unchanged pages, and typed rows from changed leaf ranges. Existing
log rows cannot change; appended events authorize only their projection streams.
Auth heartbeats still require explicit permission and the bounded reconnect proof.
Cancellation and the exact held PID are checked again immediately before stopping.

Receipts use `databaseProofMode: stopped-clone-pages-v1`, a versioned
`databasePageProof`, and `completeDatabaseContinuity: verified-pages`. They omit
`rowsByteIdentical`: no legacy whole-history hashes were computed. Installed-update
completion checks still bind the receipt to the attempted and installed artifact.
Historical replay through the legacy hash verifier explicitly refuses this proof
kind; it requires the original immutable stopped baseline for a separate replay.

A changed schema, missing WAL mark, unsupported layout, or uncertain snapshot uses
the existing complete typed comparison against the immutable stopped backup.
These fallback reads can still be expensive. An unheld/manual update keeps its
original full verification path. The fast path bounds changed-row decoding, not
all filesystem I/O: checkpointed main pages may still need a sequential comparison.

If verification fails after page-mode activation, the updater retains the new
runtime, database and recovery backup for review. It does not overwrite possible
postactivation writes or scan all history merely to decide that restoration is
unsafe. Failures before activation retain the existing pointer recovery path.
